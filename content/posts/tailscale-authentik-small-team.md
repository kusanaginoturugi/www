小規模な組織でも、サーバー、管理画面、SSH、クラウドサービスが増えると「誰がどこへ入れるか」が分かりにくくなります。

この問題を一つの製品だけで解こうとすると、設定が複雑になりがちです。ネットワークへの接続は Tailscale、Web アプリへのログインは authentik というように、役割を分けると構成を考えやすくなります。

## Tailscale は端末とサーバーをつなぐ

Tailscale は、参加させた端末とサーバーを安全なネットワークとして接続します。

たとえば、次のような用途に向いています。

- 管理者の PC から Linux サーバーへ SSH 接続する
- 社内だけで使う監視画面や NAS を外出先から開く
- 自宅や小規模事務所のサーバーを、ルーターのポート開放なしで管理する
- 端末ごとにアクセスできる範囲を制限する

重要なのは、Tailscale は「ネットワークへ入れる端末」を管理する役割だという点です。公開サイトの利用者全員に入れてもらうものではなく、運用者や社内メンバー向けの経路として使います。

## authentik は Web アプリのログインをまとめる

authentik は、Web アプリの前段に置ける認証基盤です。

アプリごとに別々の ID とパスワードを持つ代わりに、ログイン方法を集約できます。対応するアプリなら SSO を設定でき、対応していない古い管理画面でもプロキシ認証で保護できる場合があります。

たとえば、次のような用途があります。

- Redmine や社内ポータルへ多要素認証を追加する
- 外部協力者に期限付きで管理画面へのアクセスを渡す
- 退職・契約終了時に、認証基盤側でアクセスを止める
- アプリごとの利用者一覧を整理する

authentik は「その Web アプリを誰が使えるか」を管理する役割です。サーバーへ SSH できるかどうかとは別に考えます。

## 役割を混ぜない構成にする

たとえば、次のように分けます。

| 対象 | 主な仕組み |
|---|---|
| Linux サーバーの SSH | Tailscale |
| 社内だけの監視画面 | Tailscale |
| 利用者も使う Web アプリ | authentik + HTTPS |
| 管理画面 | authentik、必要なら Tailscale も併用 |

管理画面の重要度が高い場合は、Tailscale に参加した端末からだけ到達できるようにし、その上で authentik のログインも要求する二段構えにできます。

一方で、社外の利用者が使うサービスを Tailscale 前提にすると、端末設定の負担が大きくなります。その場合は通常の HTTPS 公開にして、authentik やアプリ自身の認証で守る方が運用しやすいことがあります。

## 既存環境から始める手順

いきなり全システムを移行する必要はありません。まずは次の順番が現実的です。

1. 管理対象のサーバーと管理画面を一覧にする
2. SSH 用に Tailscale を導入し、不要なポート開放を止める
3. 利用者が多い管理画面を一つ選び、authentik で保護する
4. 利用者の追加・削除手順と、障害時の戻し方を記録する
5. 運用できると確認してから対象を増やす

製品を増やすことよりも、誰が何に入れるかを説明できる状態にする方が重要です。既存システムを大きく作り替えず、アクセス経路と認証を少しずつ整理できます。

## 相談できること

SHOWWAY では、既存の Rails、PHP、Redmine、Linux サーバーなどを前提に、Tailscale と authentik を含むアクセス・認証構成の整理に対応しています。

現在のネットワーク、利用者、管理画面を確認し、「公開するもの」「社内だけにするもの」「誰に使わせるか」を分けるところから進めます。
